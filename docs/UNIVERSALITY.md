# Универсальность: как адаптировать CoverCraft под новый профиль

CoverCraft отделяет **универсальную логику** от **кандидат-специфичных
данных**. Логика (движок аудита, фит-матчер, парсер правил, проверка ширины)
не меняется — меняется только данные, и они живут в одном
файле на кандидата.

## Что универсальное, а что чужое

| Слой | Файл | Зависит от кандидата? |
|------|------|----------------------|
| Движок аудита | `internal/audit/audit.go` | Нет — чистые проверки (дубли, контактные строки, инварианты, ширина) |
| Загрузчик правил | `internal/audit/rules.go` | Нет — парсит данные в структуру |
| Фит-матчер | `internal/fit/*.go` | Частично — `DefaultConcepts` всё ещё хардкод (см. «Ограничение») |
| Правила кандидата | `context/.audit-rules.md` | **Да** — единственный кандидат-специфичный файл |

**Без файла профильные проверки выключены.** Кандидат-специфичных списков
в Go-коде нет и быть не должно — иначе хардкод одного кандидата вернётся в
движок. Единственное исключение — намеренно крошечный словарь
`infraCommonWords` в `audit.go`: языки (go/python/java/rust) и слова, которые
физически не могут быть фактом о навыке (CPU, RAM, SSD, HTTP, REST, RPS, GB).
Без него CamelCase-guard ругался «CPU заявлен как свой инструмент» на живом
письме. Всё, что может быть заявлением о навыке или инструменте, — в профиле.
Если `.audit-rules.md` отсутствует, аудитор работает только на универсальных
проверках (структура письма, ширина, контакты, CamelCase-guard по профилю),
а обязательства по фактам, атрибуция метрик, запрет чужого стека и
claimable-термины **не работают**: письмо с выдуманным фактом уйдёт молча.
Сервер пишет об этом `warn` в лог при каждом `/api/generate`.
Синтаксическая ошибка в файле даёт тот же результат, плюс текст ошибки в лог.

## Обязательная структура письма

Пять структурных инвариантов проверяет аудит, и все пять **названы в
системном промпте** — иначе модель не может дать то, чего не просили, и
получается нелечимый цикл автоправки:

1. секция «Адаптация под ваш стек»;
2. строка стека с префиксом «Стек: » (маркер секции адаптации её **не**
   заменяет — отдельная проверка);
3. строка контактов — **только если контакты есть в профиле**; проверка живёт
   в `CheckProfile`, потому что `Check` профиля не видит. Требовать её у
   кандидата без контактов в `context/` значит заставить модель выдумать
   телефон или ник;
4. финальная строка;
5. запрет самоуничижительного начала буллета («не работал / опыта нет»).

Единственный источник правды — `audit.PromptContract`: список пар
`Key`/`Marker`/`Warn`. `settings.DefaultSystemPrompt` берёт оттуда маркеры,
`Check`/`CheckProfile` — тексты предупреждений. Два теста в пакете
`internal/settings` держат обе стороны: `TestDefaultSystemPromptCoversAuditContract`
(промпт упоминает каждый маркер) и `TestAuditContractEntriesAreEnforced`
(аудит реально выдаёт каждое предупреждение). Разойтись молча они больше не
могут.

## Как добавить нового кандидата

Все файлы одного кандидата живут в одном плоском каталоге `context/`
(его ищет `main.go: contextDir()` — рядом с бинарником или в текущей
папке). Другой кандидат = замена содержимого `context/`, не подкаталог.

1. Положите файлы кандидата в `context/`: `profile.md` и все остальные
   `*.md` (системный промпт, персональные документы) — читаются по алфавиту.
2. Скопируйте шаблон правил и заполните под кандидата:
   `docs/templates/.audit-rules.md` → `context/.audit-rules.md`.
3. Заполните `## claimableTerms` и `## infraNeutralWords` своими терминами
   (в шаблоне дан базовый набор) и добавьте `## stackForbidden`,
   `## obligations`, `## metricRules` под свой профиль. Пока секция пуста,
   соответствующий класс проверок молчит.
4. Соберите бинарник — правила подхватываются без перезапуска
   (`LoadProfileRules` читает файл при каждом `/api/generate`).

Ничего в Go-коде менять не нужно.

## Формат `.audit-rules.md`

Файл — построчный: `## секция` открывает блок, внутри — строки
`ключ: значение` (значение режется по **первому** двоеточию, поэтому сам
регулярка может содержать `:`), пустая строка — разделитель блоков.
Комментарии начинаются с `#` (один символ). Все секции **опциональны**:
пустая или отсутствующая секция = этот класс проверок выключен.

| Секция | Ключи | Что делает |
|--------|-------|-----------|
| `## obligations` | `need:` `has:` `fact:` | Если в вакансии попадается `need`, но в письме нет `has` — предупреждение «потерян факт: fact» |
| `## metricRules` | `metric:` `owners:` `fact:` | Метрика в письме обязана атрибутироваться владельцу из `owners` (одна строка, несколько owner'ов через `\|`) |
| `## stackForbidden` | одно слово/токен на строку | Запрещённые в профиле стеки — письмо не должно их вводить как свои |
| `## claimableTerms` | `термин` либо `термин: сообщение` | Термин-«заявлен как опыт» — в профиле его нет; защита от выдумывания. Сообщение генерируется, если не задано |
| `## infraDomainTerms` | одно термин на строку | Инфраструктурные термины (для ширины-проверки) |
| `## infraNeutralWords` | одно слово на строку | Нейтральные слова (для ширины-проверки, без case) |

Пример `obligations` (вакансия-триггер + обязательный факт):

```
## obligations
need: (?i)react|frontend|веб-разраб
has: (?i)react
fact: React обязан быть в буллетах (frontend-профиль)
```

Пример `metricRules` (атрибуция метрики):

```
## metricRules
metric: (?i)120\+ компонент
owners: (?i)design system
fact: 120+ компонентов — только Design System
```

> Регулярки — синтаксис Go (`regexp`). Экранируйте спецсимволы:
> `+` → `\+`, `[` → `\[` и т.д. `(?i)` — регистронезависимость.
>
> **Ловушка ASCII.** `\w`, `\W`, `\b`, `[[:alpha:]]` в Go regexp работают
> **только по ASCII**. После кириллицы они не срабатывают: `\b` не находит
> границу слова, а `\w+` не матчит «ы». Проверка «искусственный интеллект» с
> `искусственн\w+ интеллект` молча переставала ловить заявку. Для русских
> слов пишите `\p{L}` или явные классы `[а-яё]`, а не `\w`/`\b`.

## Проверка

```sh
go test -count=1 ./internal/audit/ ./internal/fit/
```

- `TestLoadProfileRules*` — парсер, сброс правил и поведение без файла.
- `TestTemplateGivesWorkingProtection` — шаблон нового профиля остаётся
  рабочим (если он снова опустеет, новый кандидат останется без защиты).
- `TestAuditUniversalNoForeignFalsePositive` — чужой профиль со своими
  правилами НЕ вызывает правила другого кандидата.
- `TestGoldenUniversal` — детерминированный фит не выдаёт ложный «apply»
  на чужом профиле.
- `TestDefaultSystemPromptCoversAuditContract` / `TestAuditContractEntriesAreEnforced`
  — промпт и аудит не расходятся (см. «Обязательная структура письма»).
- `TestNoCandidateDataInEngine` — исполняемый код не ссылается на фикстуры:
  кандидат-данные не могут утечь в движок.
- `TestProfileRulesOnlyFromContextDir` — правила читаются ровно из
  `<dir>/.audit-rules.md`; посторонние файлы каталога игнорируются.
- `TestClaimPositivelyVsVacancyEcho`, `TestNegRegexHasNoEmptyAlternative`,
  `TestInfraVocabularyDoesNotFlagOrdinaryWords` — заявка ловится по термину,
  перечисление в заголовке и отрицание не дают ложного «потерян факт»,
  а CPU/RPS/SSD не читаются как инструменты.
